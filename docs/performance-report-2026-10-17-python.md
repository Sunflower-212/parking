# 性能实测报告

测试日期：2026-10-17。基线提交 `797313c`，优化版为本次发布代码。所有数据来自隔离的 `parking-benchmark`，没有向日常数据库灌入测试数据。

## 环境与方法

- Windows / Docker Desktop Linux Engine 29.8.0；Intel i9-13900HX（24 核、32 线程）；Docker 可见 32 CPU、15.48 GiB 内存。
- 两版均使用 Java 17、JVM 最大堆 1 GiB、Hikari 20、MySQL 8.4.4 / 缓冲池 1 GiB；两个 Redis 分别保存状态和缓存。该基准编排没有单独的容器 CPU 限额，日常部署另有内存上限。
- 10 万用户、100 个停车场、10 万车位、100 万入场记录、100 万订单、20 万充值记录，覆盖一年。历史数据固定，客户端随机种子固定。
- 两版均为 100 个并发客户端，每轮预热 120 秒、采样 300 秒，各 3 轮；HTTP/1.1 持久连接、无思考时间。每个客户端使用独立用户和车位，集中访问一个楼层。争抢同一车位另由集成测试验证。
- 操作选择为 80% 读取、20% 预约；每次成功预约配对取消，因此按实际 HTTP 请求计数写比例约 33%。RPS 包含预约和取消。
- 基线调用旧收入、用户订单列表、整楼层接口；优化版调用统一统计、用户分页、实时状态接口。统一统计包含更多指标。这是对应业务场景比较，不是完全相同响应体的单条 SQL 对比。
- 同机其他已有服务保持运行；不是独占硬件或云服务器容量承诺。最早短连接客户端耗尽 Windows 临时端口的结果已作废，两版均以修正后的客户端重新完整测量。

## SQL、索引和写入成本

单独清空缓存后，超级管理员统计冷请求为 **6 条业务 SELECT、174.98ms**；随后 20 次命中请求 P95 为 **7.09ms**。该探针在无并发负载时执行，不能替代 100 并发未命中的 P95。

| EXPLAIN ANALYZE 场景 | 基线 | 优化版 |
| --- | --- | --- |
| 用户订单取 20 条 | 扫描 100 万行，排序，129ms | 覆盖索引读取 10 条，无额外排序，0.0213ms |
| 近七天收入 | 扫描 100 万行，临时聚合，141ms | 时间索引范围读取 18,751 行，仍需按日聚合，25.2ms |
| 停车场 1 首个空位 | 主键首行即命中，0.0153ms | 可用车位覆盖索引首行命中，0.0373ms |

空位探针原本已很快，本样本没有加速；新索引的收益不能由这个最佳分布样本外推。包含搜索仍可能扫描，未宣称前置通配符可由普通索引优化。

另在专用临时库分别复制 100 万订单，原索引与新索引各执行三次 5,000 条批量插入并提交（交替执行顺序）。以下为数据库端耗时，不含 HTTP 和网络；不同于并发预约事务，不代表所有写场景。临时库完成后已删除。

| 订单索引 | 二级索引空间 / MiB | 插入 5,000 条三次 / ms | 中位 / ms |
| --- | ---: | --- | ---: |
| 基线 | 0.00 | 32.22, 33.13, 29.83 | 32.22 |
| 优化 | 93.70 | 55.11, 71.22, 60.39 | 60.39 |

增加索引需要额外存储、写入和维护；同时移除被复合索引覆盖的单列索引、复用楼层坐标唯一索引，保留业务唯一约束与外键。索引空间来自 InnoDB 页统计，是测试数据下的分配量。

## 目标与局限

- 常用分页与楼层 P95 ≤300ms：本次满负载仍有超标，不能标记达成。
- 预约/取消 P95 ≤500ms：部分轮次超标，不能标记全部达成。
- 统计缓存命中 ≤150ms：独立热缓存探针通过，混合负载统计 P95 也低于目标；未按命中状态单独标记每个压测请求。
- 统计未命中 ≤800ms：独立冷请求通过；尚未单独量测 100 并发冷缓存 P95。
- 非预期错误率 <0.1%、冷统计 ≤8 条 SQL、首屏 gzip JS 减少 ≥30%：本次通过。
- LCP ≤2.5 秒、CLS ≤0.1：当前固定本地浏览器条件通过，不能代表弱网和低端设备。
- 后端真实 MySQL/Redis 并发与恢复测试、三角色浏览器与移动宽度测试另见验证记录；第三方真实支付/OCR/AI/OSS 联调不在本报告范围。

满负载的后续优化应根据请求耗时和连接池等待进一步定位，优先减少同停车场高并发写入持锁时间和楼层状态响应开销；不得通过缓存实时占用或跳过数据库约束换取低延迟。
